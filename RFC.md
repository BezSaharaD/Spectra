# RFC: Ядро линтера (JS/TS) — архитектура

**Статус документа:** Living document / в процессе структурирования
**Периметр языков:** JavaScript + TypeScript (единый периметр анализа; TS исторически более актуален для крупных проектов, JS рассматривается как подмножество той же модели)
**Область документа:** Ring 0 (Core Parser) + Ring 1 (Analysis Engine) + точки соприкосновения с Wrapper. Wrapper как таковой (политики, конфигурация, режимы) описан только в той мере, в которой влияет на границы Ring 0 / Ring 1.

---

## 0. Руководящие принципы (критерий при любом споре)

1. **Ничего не выкидываем.** Любой узел, любой мусор, любой непарсящийся фрагмент остаётся в графе — как узел с флагами недостоверности (раздел 8), а не как исключение из анализа.
2. **Когда не можем доказать — делаем больше (overapproximate). Когда можем доказать — доказываем точно.** Действует для инвалидации кэша, confidence-модели, alias-анализа, порогов насыщения контекста.
3. **Гибкость важнее производительности.** Конкуренция не в скорости, а в том, что умеем анализировать то, что другие инструменты не могут.
4. **Core не содержит политики.** Ядро только вычисляет факты о коде и помечает их достоверность. Решение «репортить недостоверное или нет» — целиком в Wrapper.
5. **Core не исполняет решения правил, только отвечает на структурные вопросы о коде.**
6. **Ни одно решение в этом документе не является постоянным по умолчанию.** Каждое архитектурное решение сопровождается статусом и явным условием пересмотра (см. раздел 0.1). Отсутствие явного триггера — не значит «решение вечное», значит «триггер ещё не сформулирован».

Принципы 4–5 конкретизированы буквальным разделением ядра на два кольца (раздел 1): Ring 0 не содержит вообще никакой аналитической логики (только построение структуры), весь анализ и вся работа с правилами — Ring 1. Wrapper остаётся чистой политикой поверх Ring 1.

### 0.1 Конвенция статусов решений

Каждая запись в Журнале решений (раздел 12) обязана иметь:
- **Статус**: `provisional` (принято на основе текущих аргументов, подлежит пересмотру) / `blocked` (осознанно отложено до появления данных) / `policy exception` (осознанное точечное нарушение общего принципа, см. раздел 1.1) / `eliminable-if-unproven-necessary` / `mergeable-if-proven` / `rejected` (рассмотрено и явно отклонено, с обоснованием)
- **Revisit Trigger** — конкретное условие пересмотра, не абстрактное «если что-то пойдёт не так»

### 0.2 Necessity-First (лучший код — ненаписанный код)

Перед оптимизацией любого компонента — сначала вопрос «а нужен ли он вообще в этом объёме, или можно не строить», а не только «как сделать дешевле».

**Критическое ограничение принципа (сформулировано по итогам разбора EC-1, раздел 11.3):** применяется **только к инфраструктурной эффективности** (хранение, индексация, персистентность, вспомогательные структуры ускорения доступа). **Никогда не применяется к аналитической способности/точности механизма** — то есть нельзя откладывать/убирать саму способность различать паттерны кода под лозунгом «пока не доказана необходимость», если это уменьшает то, что система способна увидеть. Это прямой конфликт с принципами 0.1 и 0.3. Точность можно **удешевить** (найти более дешёвый путь к той же точности), но не **отложить как неважную**.

### 0.3 Формат Consolidation/Elimination Candidate

Используется, когда рассматривается слияние двух компонентов или отказ от структуры — без немедленной фиксации решения, так как обменный курс между выигрышем и издержками не переносится по аналогии между местами системы, а определяется локально.

```
### [Elimination | Consolidation] Candidate: <название>
Компоненты: ...
Что выигрываем: <ось>
Что платим: <ось, не обязательно та же>
Локальный обменный курс: не фиксирован заранее, определяется на месте
Статус: eliminable-if-unproven-necessary / mergeable-if-proven
```

## 1. Трёхуровневая архитектура: Ring 0 / Ring 1 / Wrapper

```
┌───────────────────────────────────────────────┐
│                   WRAPPER                      │
│  - решает: репортить недостоверные результаты  │
│    или нет (по режиму)                         │
│  - конфигурация, режимы, загрузка Rule IR       │
│    артефактов в Ring 1                          │
└───────────────────┬─────────────────────────────┘
                     │  raw findings (флаги достоверности + факты)
┌────────────────────▼──────────────────────────┐
│                   RING 1                       │
│         (Analysis Engine + Rules)              │
│  - принимает артефакт Ring 0 + Rule IR          │
│  - Query Engine (structural + stateful VM)      │
│  - Fused Pull-Push execution model              │
│  - demand-driven производные анализы            │
│    (alias-summary через CFL-reachability,       │
│     дорогие опциональные факты)                 │
│  - НЕ содержит политики репортинга              │
└────────────────────┬─────────────────────────────┘
                     │  артефакт (граф + метаданные + Requirement Set)
┌────────────────────▼──────────────────────────┐
│                   RING 0                       │
│              (Core Parser)                     │
│  - «тупой парсер»: строит AST/IR/CFG/DFG/       │
│    Symbol Tree/Call Tree/Dependency Graph       │
│  - помечает флаги недостоверности               │
│    (в т.ч. is_reliable на неразобранных блоках) │
│  - инкрементальный парсинг + Node Identity      │
│  - принимает Requirement Set как доп. вход      │
│    (см. Policy Exception #1, раздел 1.1)        │
│  - НЕ содержит никакой семантики правил         │
│  - результат — переносимый артефакт             │
│    (сериализуется на диск, коммитится в git)    │
└─────────────────────────────────────────────────┘
```

**Ключевое разделение:** Ring 0 не отдаёт диагностики/violations вообще — он отдаёт только **структурный артефакт анализа** (граф + Node Identity + флаги недостоверности). Весь смысловой анализ, включая работу с правилами, происходит в Ring 1, который потребляет этот артефакт.

**Реализация:** Rust как основной язык обоих колец; допускается asm или другие языки для отдельных горячих путей, по необходимости.

**Правила:** пишутся на JS сторонними разработчиками, компилируются один раз в Rule IR артефакт — локальный артефакт пользователя (передаётся, например, через git). Core (оба кольца) не распространяет чужие правила как часть продукта — проблема доверия/защиты снята по построению (раздел 6.2).

### 1.1 Policy Exceptions Log

Формальный реестр точечных, осознанных нарушений общих политик раздела 0/1 — с обоснованием, почему нарушение локально оправдано и не отменяет общий принцип.

**Policy Exception #1: Ring 0 принимает Requirement Set**

- **Нарушаемая политика**: Ring 0 спроектирован как «тупой парсер», не имеющий знания о правилах, работающий batch-проходом без обратной связи.
- **Конкретное нарушение**: Demand-Driven Auxiliary Analysis Pattern (раздел 7.1) требует, чтобы Ring 0 получал на вход Requirement Set — производное от содержимого загруженных правил множество: какие дорогие опциональные факты реально нужны.
- **Обоснование допустимости**: исходная политика сформулирована для общего случая полного самодостаточного построения графа, не предусматривала (и не обязана была) частный случай оптимизации опциональных дорогих анализов. Ring 0 остаётся чистой функцией `(исходный код, Requirement Set) → артефакт` — не превращается в интерактивный сервис, **не обращается к Rule IR семантически, только количественно** («где нужно/не нужно строить факт X»). **Без этого исключения Demand-Driven паттерн (раздел 7.1) не работал бы вообще.**
- **Статус**: `policy exception`, `provisional`
- **Revisit Trigger**: если Requirement Set перестанет быть простым декларативным множеством и потребует усложнённой семантики (например, зависящей от промежуточных результатов самого построения графа) — **сигнал, что грань между «тупым парсером» и «аналитическим сервисом» стёрлась по факту, раздел 1 требует пересмотра границы колец целиком**.

## 2. Данные и представления (Ring 0)

### 2.1 AST

Полное синтаксическое дерево, строится через error-tolerant парсер (раздел 4). Хранит узлы синтаксиса как есть, включая комментарии/trivia, прикреплённые к ближайшему узлу (non-lossy парсинг — свойство парсера, не отдельный «слой анализа»; Ring 0 не интерпретирует их смысл).

**Позиции узлов**: хранится только byte-offset (`u32`, начало/конец), не line/column. Line/column вычисляются лениво через бинарный поиск по единой таблице переводов строк на файл.

**Текстовые данные узлов**: zero-copy ссылки `(offset, length)` на исходный текст, без копирования строк.

**Статус**: `provisional`. **Revisit Trigger**: нет известного на данный момент.

### 2.2 IR — Three-Address Code (TAC)

Плоская форма (по духу — аналог RTL/LLVM IR). Выбрана вместо ANF/CPS и Expression-graph: те не дают дополнительной выразительности сверх TAC + explicit closures/suspend-инструкций, при существенно большей сложности реализации.

Расширения TAC под JS/TS:
- `closure_create(capture_list)` — явный список захваченных переменных
- `property_read(obj, field)` / `property_write(obj, field, value)` — частичная запись, не абстрактное «use» объекта целиком
- `element_read` / `element_write` для массивов и computed-доступа
- `spread_expand` для `...args`
- suspend-инструкции для `await` / `yield`

**AST и IR сосуществуют постоянно** — не дублирование, а разные уровни абстракции: **стилистические правила работают по AST, семантические — по IR/CFG/DFG, гибридные джойнят оба через маппинг**.

**Маппинг AST↔IR:** каждый IR-узел несёт `source_ast_id` + флаг `is_synthetic`; обратный индекс `ast_id → Set<ir_node_id>`.

**Статус**: `provisional`. **Revisit Trigger**: нет известного на данный момент.

### 2.3 Словарь десугаринга (DSL-based)

Вместо инлайновой полной развёртки каждой конструкции (`for-of`, `async/await`, деструктуризация и т.д.) в каждом месте использования — словарь, заданный через **DSL** (гибкость приоритетнее скорости сборки словаря).

- Словарь хранит **полностью развёрнутую версию** каждой конструкции, по стадиям (многие конструкции разворачиваются в несколько этапов: `async/await → generator → state machine → TAC`)
- IR хранит только **ссылку на конструкцию + ключ в словарь**
- Правило запрашивает нужный уровень развёртки через query API (`expand_level: Syntax | Semantic | Full`)

**Статус**: `provisional`. **Revisit Trigger**: нет известного на данный момент.

### 2.4 CFG — построен полностью

Явно моделирует implicit control flow сахара: `?.`, `??`, `&&`/`||`, `for-of` (протокол итератора + неявный `try/finally`).

- **Suspend-edges** — отдельный тип ребра для `await`/`yield` (не обычное control-ребро)
- Режимы обхода параметризованы явно:
  - `Sync` — suspend-рёбра игнорируются
  - `Async` — только suspend/continuation-рёбра
  - `Full` — оба

**Статус**: `provisional`. **Revisit Trigger**: нет известного на данный момент.

### 2.5 DFG — occurrence-level, с частичными записями и асимметричной heap-моделью

- Гранулярность — каждое конкретное чтение/запись, не агрегат на уровне переменной
- **Partial writes**: `obj.field = x` — явная мутация конкретной location, не «use» всего `obj`
- **Heap model — асимметричная:**
  - **Allocation-site модель** (каждый литерал/`new` — уникальная точка аллокации) — строится **всегда**. Дешёвая, основа для confidence-модели (включая флаг `dynamic_unresolvable`, раздел 8). Подтверждено обязательной под Necessity-First оптикой (раздел 11.3, Confirmed Necessary).
  - **Name-based (path-based) модель** (location по пути доступа, `obj.a.b`) — строится **demand-driven** через общий паттерн раздела 7.1: только если presence-check по загруженному Rule IR обнаруживает хотя бы одно правило, реально использующее path-based факты. Построение — отдельным этапом после основного fused pull-push прохода (раздел 6.3), с ранним выходом, **чтобы не портить cache-locality главного прохода**.

**Историческая заметка (изменение решения):** ранее принималось решение «обе модели одновременно, не fallback одной к другой» с мотивировкой кросс-валидации фактов между моделями. В текущей версии модель асимметрична: allocation-site всегда, name-based demand-driven. Как следствие изменения — **механизм кросс-валидации между моделями и уточнения точности при конфликте между их предсказаниями (грубый ответ → точный пересчёт) в текущей архитектуре отсутствует**. Это открытая точка: если правило запрашивает name-based факты и они расходятся с allocation-site, механизм разрешения конфликта не сформулирован — фиксируется как открытый вопрос (раздел 13).

**Статус**: `provisional`.
**Revisit Trigger**: если подавляющее большинство rule-сетов всегда запрашивают path-based факты — demand-driven presence-check становится чистым накладным расходом без экономии, стоит вернуться к «всегда обе модели».

### 2.7 Symbol Table / Scope Tree

**Открытый вопрос.** Присутствует на всех диаграммах архитектуры с начала обсуждения, но модель не проработана: отдельная структура или ещё один набор типизированных рёбер поверх AST/IR (resolution-edges: identifier → declaration)? Как моделируются `var`-hoisting, TDZ для `let/const`, hoisting функций — через тот же механизм словаря десугаринга (2.3) или отдельно?

**Стоимость Demand-Driven для hoisting/TDZ-анализа** — `blocked`, требует данных (раздел 12): нельзя решить, нужен ли Demand-Driven механизм для этой части, пока не спроектирована сама модель Symbol Table и не измерена относительная стоимость hoisting/TDZ-анализа по сравнению с построением AST/IR/CFG.

### 2.8 DFG Construction Mode

Способ построения occurrence-level DFG (раздел 2.5) параметризован флагом:
- `Eager` — строится для всего проекта сразу
- `Scoped` — строится только для scope'ов, требуемых загруженным набором правил, через общий паттерн раздела 7.1 (pre-scan Requirement Set **до** начала однопроходного построения в Ring 0, сохраняя инвариант батч-природы Ring 0)

**Явное отступление от общей политики раздела 1** (Ring 0 самодостаточен) — задокументировано как Policy Exception #1 (раздел 1.1): общая политика покрывает типичный случай полного построения, но не предусматривала частный краевой случай оптимизации опциональных дорогих анализов.

**Статус**: `provisional`.
**Revisit Trigger**: если granularity «scope» (функция vs файл vs блок) окажется слишком грубой/тонкой на практике — потребуется пересмотр единицы измерения.

### 2.9 Call Tree, Dependency Graph

Строятся поверх IR/CFG/DFG как дополнительные отношения того же графа (реляционная модель, раздел 6.2).

**Consolidation Candidate:** возможное слияние Call Tree и Dependency Graph в единую структуру с типизированными рёбрами (`call` / `import` / `type-reference`) вместо двух отдельных графов.

- Что выигрываем: один join-механизм вместо двух, меньше кода для инвалидации/SCC
- Что платим: возможное снижение читаемости запросов при смешении гранулярностей (функция vs модуль)
- Локальный обменный курс: не perf, а ясность кода запросов — определяется экспериментом (написать реальные query на обеих моделях, сравнить)

**Статус**: `blocked`, добавлено в раздел 12 (Данные, необходимые перед принятием решения).

**Transitive closure (Dependency Graph):** не хранится полное предвычисленное замыкание. Вместо этого — summary-based подход по аналогии с alias-analysis (раздел 6.1): memoized query «зависимости модуля X до глубины K», кэшируемый через общую Salsa-инфраструктуру.

**Статус**: решено, `provisional`.

### 2.10 Type Layer

Периметр языков — JS **и** TS — это **меняет статус вопроса** «нужен ли слой типов». Раз TS в периметре — типовая информация физически присутствует в части исходников (аннотации, TS type system) и не может игнорироваться как факультативная тема. Решение по объёму и способу построения (использовать ли существующий TS-checker как источник типов для типизированных файлов, что делать с чистым JS — best-effort inference или явный отказ) — **требует отдельного, ещё не проведённого разбора**, зафиксировано как направление, а не закрытый пункт.

## 3. Node Identity (Ring 0)

Content-addressed хэширование снизу вверх (Merkle-tree подход): `hash(node) = hash(node_kind, hash(children...))`.

При любой неоднозначности матчинга между старой и новой версией дерева — дефолт: считать другим узлом (новый ID, инвалидация). Реализация принципа «лучше больше инвалидации, чем меньше» на уровне алгоритма идентичности.

**Physical Structural Sharing:** если content-hash поддерева совпал со старой версией — поддерево не копируется заново, а физически переиспользуется (тот же блок памяти/ссылка). Прямое следствие принципа идентичности, дающее одновременно **экономию памяти (дедупликация структурно идентичных фрагментов) и скорость (инкрементальный пересчёт не требует копирования неизменных соседей)**.

**Важное разграничение (см. раздел 8.1):** этот хэш — быстрая, **не криптографическая** функция, оптимизированная под горячий путь (вызывается на каждый узел при каждой инкрементальной перестройке). Он **не является** гарантией целостности артефакта — это отдельный, самостоятельный механизм (раздел 8.1).

**Статус**: `provisional`. **Revisit Trigger**: нет известного на данный момент.

## 4. Парсинг (Ring 0)

### 4.1 Стратегия восстановления после ошибок

**Вариант B: error-tolerant grammar** (в духе rust-analyzer/tree-sitter). Грамматика изначально спроектирована так, что «неправильные» конструкции — тоже валидные узлы дерева, помеченные флагом `syntax_broken` (раздел 8), а не panic-mode пропуск токенов до синхронизирующей точки. Прямое следствие принципа «граф ничего не выкидывает» — вариант A (panic-mode) терял бы часть исходного текста при пропуске до точки синхронизации.

**Статус**: `provisional`. **Revisit Trigger**: нет известного на данный момент.

### 4.2 Инкрементальный парсинг

Гибридная модель: сначала определяется, **что именно изменилось** в правке (diff по тексту/AST-региону), и в зависимости от характера изменения выбирается стратегия перестройки:
- изменение, не влияющее на структуру (например, содержимое комментария) — не требует перестройки дерева вокруг него
- структурное изменение — перестраивается только затронутое поддерево, далее в дело вступает Node Identity (раздел 3)

Это не полный edit-aware reparse «в стиле tree-sitter» и не наивный full-reparse-с-нуля-каждый-раз — комбинация: дешёвая проверка характера изменения перед выбором объёма перестройки.

**Статус**: `provisional`. **Revisit Trigger**: нет известного на данный момент.

### 4.3 Параллелизм построения графа файлов

Построение AST/IR/CFG отдельного файла не зависит от других файлов — зависимость появляется только на уровне Symbol resolution / Dependency Graph / межфайлового DFG. Стадия «распарсить и построить локальный IR/CFG каждого файла» распараллеливается по ядрам CPU без компромиссов (частично закрывает открытый вопрос №4, раздел 13).

**Статус**: `provisional`.

## 5. Границы графа и артефакт (Ring 0)

Граф строится **сразу для всего проекта** (eager, whole-project, не лениво по требованию — на уровне структурного графа AST/IR/CFG/Call Tree; DFG и SCC могут иметь Scoped-режим, см. 2.8 и 7). Результат — **переносимый артефакт**, который:
- сериализуется на диск (раздел 5.1)
- может передаваться между людьми/машинами через git (**явное требование: воспроизводимость и разделяемость результата построения графа без повторного парсинга у каждого участника**)

**Исходный текст НЕ хранится внутри артефакта** — только offset-ссылки на файл на диске. Решено однозначно: хранение копии исходника внутри артефакта избыточно (дублирует то, что уже есть в репозитории) и потенциально опасно (риск рассинхронизации).

**Статус**: `provisional`.
**Revisit Trigger**: появление данных о масштабах, на которых whole-project eager построение перестаёт быть практичным (раздел 12).

### 5.1 Персистентность

Кэш/артефакт хранится **и в памяти процесса, и на диске** между независимыми запусками.

**Модель записи на диск — параметризуемая N-уровневая (size-tiered), включая вырожденный случай:**

```
WAL Config (задаётся Wrapper'ом):
  levels: Vec<SizeThreshold>   // 0..N уровней, число выбирает пользователь/команда
  merge_mode: Direct | Tiered  // Direct = запись сразу в снапшот, без WAL вообще
```

`Direct` — не временная заглушка, а полноправный режим (частный случай `Tiered` с `levels: []`). Не два отдельных кода-пути — один параметризуемый механизм.

Принцип уровней — size-tiered compaction (аналог LSM-tree подхода): маленькие частые изменения попадают в «горячий» верхний уровень, компактятся вниз по достижении порога **размера** diff, не количества записей. Калибровка порогов ориентируется на естественные временные паттерны разработки (коммит / день / неделя / год) — конкретные числа не фиксируются, требуют данных (раздел 12).

**Формат хранения (сжатый vs zero-copy несжатый) — заблокирован.** Выбор между компактным для git сжатым форматом и zero-copy несжатым форматом (для быстрой mmap-загрузки, раздел 11 PW-6) требует расчётного/измеренного веса типичного артефакта, которого пока нет.

**Статус**: `blocked` (пороги, формат), решено (параметризуемая модель как таковая).
**Revisit Trigger**: наличие оценки веса артефакта и распределения размеров diff по реальным open-source проектам (раздел 12).

## 6. Ring 1 — Analysis Engine

Ring 1 принимает на вход артефакт Ring 0 (с диска или из памяти) и скомпилированные Rule IR артефакты, производит **сырые находки** (facts/violations с флагами достоверности), не принимая решения о репортинге.

### 6.1 Alias analysis — Summary-based, через CFL-reachability (Ring 1, demand-driven)

Отклонён явный k-CFA (перечисление контекстов вызова) из-за комбинаторного роста `O(N^k)`.

**Принятая модель:**
1. Для каждой функции считается одно обобщённое **summary** — abstract-отношение «алиасинг на входе → алиасинг на выходе», не зависящее от конкретного контекста вызова
2. На каждом call-site summary инстанцируется конкретными аргументами (дешёвая подстановка, не повторный анализ тела функции)
3. Корректность context-sensitivity обеспечивается через **CFL-reachability** — call/return-рёбра графа вызовов помечаются как парные скобки, путь валиден только при их сбалансированности

Итоговая асимптотика: `O(N + k)` вместо `O(N^k)`.

**Оговорка о точности:** метод точен без потерь для дистрибутивных flow-функций; для may-alias (то, что нам нужно при консервативном подходе) — укладывается в схему без потери прецизионности сверх допустимого.

**Интеграция с остальной архитектурой (без новых механизмов):**
- summary — ещё один вид memoized query в общей Salsa-инфраструктуре (раздел 7), кэшируется и инвалидируется по тому же графу зависимостей
- взаимно рекурсивные функции схлопываются в SCC (Kosaraju), summary считается совместно, итеративно до fixpoint — тот же механизм, что и для dataflow над циклами CFG
- вычисляется **demand-driven** (pull): не для всей программы заранее, а по запросу конкретного правила

**Context Budget:** не infinite — **bounded с overflow-флагом**. При превышении порога оставшиеся контексты схлопываются в единый merged-контекст (**консервативная деградация точности**), узел помечается флагом `context_saturated` (раздел 8) — **отдельным от прочих флагов недостоверности, так как причина иная (осознанное ограничение бюджета, а не непонятный код)**.

Порог — конфигурируемый параметр, не хардкод.

**Data Requirements Roadmap для определения порога** (порог не фиксируется на этапе дизайна):
1. Распределение количества уникальных call-site контекстов на функцию — по представительной выборке реальных JS/TS проектов разного масштаба и стиля (обычные приложения vs library-код с обилием higher-order generic функций)
2. Стоимость памяти на один закэшированный контекст — замер после появления рабочей реализации
3. Корреляция между стилем кодовой базы (функциональный/ООП, degree of polymorphism) и скоростью роста числа контекстов — единый порог или адаптивная эвристика на проект
4. Механизм получения данных — opt-in telemetry от ранних пользователей либо прогон на корпусе публичных репозиториев до релиза

До появления этих данных — используется заведомо консервативный (маленький) дефолт порога, в согласии с принципом «когда не можем доказать — делаем больше» (здесь: **лучше чаще ставить `context_saturated`, чем не заметить реальный взрыв контекстов**).

**Важная историческая заметка (рассмотрено и отклонено):** в ходе ретроспективного аудита (раздел 11.3) предлагалось отложить реализацию всего summary/CFL-механизма до эмпирического доказательства, что flow-insensitive анализа недостаточно («build-order gate»). **Предложение отклонено.** Аргумент: context-sensitive alias-анализ — не вопрос инфраструктурной эффективности, а вопрос аналитической **способности** видеть паттерны, недоступные плоскому AST-анализу — то есть прямая реализация принципа 0.3 («гибкость важнее производительности») и ядро value proposition всего проекта. Откладывать аналитическую способность под лозунгом Necessity-First запрещено правилом 0.2. Механизм строится как спроектировано, без гейта.

**Статус**: `provisional` (механизм), `blocked` (конкретное значение порога).
**Revisit Trigger**: результаты сбора данных по пунктам 1–4 выше.

### 6.2 Query Engine

**Structural Query Layer (декларативный):**
- паттерн-матчинг внутри одного дерева — переиспользуется подход tree-sitter query language
- join-слой между разными графами (AST↔IR↔CFG↔DFG↔CallTree) — собственный минималистичный join-engine (**не полноценный даталог-движок в духе CodeQL — интеграция такого стека как библиотеки тяжелее, чем написать свой узкий join-engine**), поддерживающий произвольное число типов отношений (не захардкоженный список переходов)

**Индексы** — колоночный (SoA) layout вместо `HashMap<Key, Vec<NodeId>>`: единый массив `(key, node_id)` пар, диапазонный доступ вместо hash-lookup там, где возможно (например, тип узла — прямая индексация по номеру типа).

**Индекс «по типу узла» отдельно не строится** — сам SoA-layout, сгруппированный по `node_kind`, физически уже и есть этот индекс.

> **⚠️ Явно задокументированный риск (принято с оговоркой):** есть риск, что при дальнейшем развитии кодовой базы физический layout изменится (например, узлы перестанут группироваться по `node_kind` ради другой оптимизации), и разработчик, не осведомлённый об этом историческом решении, добавит отдельную индексирующую структуру заново, не заметив дублирования с уже существующей группировкой, либо, наоборот, удалит группировку, не подозревая, что она неявно служит индексом, и молча сломает предположение, на которое опирается Query Engine.
> **Митигация:** при реализации — явный, видимый в коде маркер/комментарий на самой структуре SoA-хранилища, прямо ссылающийся на этот раздел RFC, и сопроводительный тест, проверяющий, что запрос «все узлы типа X» действительно обслуживается напрямую через физический layout, а не через отдельную структуру. Если оба развалятся синхронно с изменением кода — тест обязан упасть, вынуждая разработчика осознанно принять новое решение, а не тихо разойтись с этим разделом документа.

**Stateful Bytecode Layer (императивный):**
- собственная лёгкая VM внутри Rust-процесса, **не WASM** — так как Core (и Ring 0, и Ring 1) не распространяет чужие правила: каждое правило — локальный артефакт пользователя, проблема изоляции от недоверенного стороннего кода отсутствует по построению
- **компиляция правила в bytecode — точка для статических проверок (например, отсутствие гарантированно бесконечных циклов) до исполнения**
- доступ к этому слою — отдельный явный API-вызов со стороны правила

**Общий intern-pool между Rule IR и артефактом Ring 0**: если оба используют согласованную схему интернирования строк — сравнение идентификаторов остаётся `int == int` сквозь всю систему, включая границу правило↔граф. Ограничивает будущее решение открытого вопроса №9 (Rule Compilation Pipeline): какой бы ни оказался механизм компиляции правил, он обязан согласовывать intern-таблицу с Ring 0.

**Статус**: `provisional`. **Revisit Trigger**: нет известного на данный момент.

### 6.3 Модель исполнения — Fused Pull-Push

Единый физический проход по графу вместо раздельных фаз «построить индексы → pull-запрос → push»:
- во время прохода одновременно (а) вычисляются дешёвые локальные (streamable) предикаты правил — **кандидаты сразу попадают в очередь правила**, и (б) как побочный эффект того же посещения узла пополняются индексы
- запросы, требующие информации вне локального контекста (forward-reference, transitive closure, alias-факты после fixpoint) — резолвятся отдельно, но **без повторного обхода графа**, через уже готовые структуры
- сам проход — memoized query в общей Salsa-модели, подчиняется той же инвалидации

**Статус**: `provisional`. **Revisit Trigger**: нет известного на данный момент.

## 7. Инкрементальность и инвалидация (сквозь Ring 0 и Ring 1)

Query-based архитектура (Salsa-подобная) с первого дня в обоих кольцах:
- Ring 0 использует её для инкрементального построения/обновления структурного артефакта
- Ring 1 использует её для кэширования query-результатов, alias-summary, совпадений правил

**Правила инвалидации:**
- ацикличный участок графа зависимостей → инвалидируется только достижимое вниз поддерево
- цикличный участок (SCC) → инвалидируется **целиком**, без попытки частичного пересчёта

**Алгоритм разложения на SCC — Kosaraju**, не Tarjan: SCC пересчитывается редко (граф строится полностью один раз, далее — точечная инвалидация), поэтому константный выигрыш Tarjan не окупает **более сложную и багоёмкую реализацию**.

**SCC Construction Mode:** аналогично DFG (раздел 2.8), параметризован флагом `Eager`/`Scoped` через общий паттерн раздела 7.1. **Дефолт — `Eager`** (обоснование: дёшево в абсолютных цифрах, SCC редки в типичном JS/TS-коде). `Scoped`-режим — низкоприоритетный extension point, **реализуемый только при обнаружении реальной необходимости**.

**Переиспользование графа зависимостей и SCC-разложения** — многократно:
1. инвалидация кэша артефакта Ring 0
2. распространение confidence-флагов (раздел 8)
3. порядок обхода для fixpoint dataflow-вычислений
4. вычисление alias-summary в Ring 1 (раздел 6.1)
5. transitive closure Dependency Graph (раздел 2.9)

**Статус**: `provisional`.
**Revisit Trigger** (для дефолта Eager SCC): активируется при обнаружении реальных монорепо, где даже eager SCC перестаёт быть «дёшево абсолютно» — конкретный сигнал: замер покажет заметную долю времени построения графа, уходящую на SCC на очень крупных проектах (раздел 12).

### 7.1 Demand-Driven Auxiliary Analysis Pattern (общий паттерн)

**Именованный, переиспользуемый архитектурный паттерн**, применяемый единообразно к:
- построению name-based heap-модели (раздел 2.5)
- `Scoped`-режиму DFG (раздел 2.8)
- `Scoped`-режиму SCC (раздел 7)
- любому будущему дорогому опциональному анализу

**Механика паттерна:**

1. **Pre-scan Requirement Set** — до начала основного построения Ring 0 выполняется статический анализ загруженного Rule IR (**на стороне Ring 1/компилятора правил**), результат — **декларативный набор требований: какие scope'ы/узлы/типы фактов реально нужны хоть одному правилу**
2. **Presence-check с ранним выходом** — конструирование конкретного дорогого факта пропускается **целиком**, если ни одно требование его не покрывает
3. **Отдельный проход, не fused с основным** — построение происходит как дополнительный этап после основного fused pull-push прохода, **чтобы не портить cache-locality горячего пути нерегулярным паттерном доступа**
4. **Точечная инкрементальность** — пересчитывается только **реально изменившееся и всё ещё входящее в requirement set** подмножество

**Статус**: `provisional`.
**Revisit Trigger**: если подавляющее большинство реальных rule-сетов запрашивают почти все дорогие факты почти всегда (presence-check почти никогда не отсекает работу) — **накладные расходы механизма перестают окупаться**, вернуться к eager-по-умолчанию для конкретного анализа.

## 8. Confidence Model

Вместо единого булева `is_reliable` — **набор специфичных флагов причины недостоверности** + один универсальный fallback.

**Историческая заметка:** изначально принималось решение о булевом `is_reliable` без градации шкалы — **сознательное упрощение**. В текущей версии заменено на набор специфичных флагов ниже, поскольку Wrapper должен различать причину недостоверности при принятии решения о репортинге. Возможная градация (числовая шкала достоверности) как альтернатива не рассматривалась заново; фиксируется как открытая возможность, не отвергнутая явно.

| Флаг | Причина | Кто выставляет |
|---|---|---|
| `syntax_broken` | Узел — точка восстановления error-tolerant грамматики, исходный текст синтаксически невалиден | Ring 0, парсер |
| `construct_unsupported` | Синтаксис валиден, но семантика конструкции не смоделирована (промах в словаре десугаринга) | Ring 0, IR-builder |
| `dynamic_unresolvable` | Статическое разрешение принципиально невозможно (`eval`, `Function()`, полностью динамический доступ) — свойство кода, не ограничение движка | Ring 0/Ring 1, DFG/alias |
| `context_saturated` | Бюджет alias-контекстов превышен (раздел 6.1) | Ring 1 |
| `unknown_edge_case` | Универсальный fallback — ситуация вне известной классификации | Любой уровень, catch-all |

**Валидационный инвариант**: `unknown_edge_case` может быть выставлен только если ни один специфичный флаг не сработал. Специфичные флаги взаимно проверяются на непересечение источников (разные, непересекающиеся стадии пайплайна — **например, если парсер уже признал узел `syntax_broken`, IR-builder дальше по нему не проверяет desugar-словарь**).

Производный булев `is_reliable` вычисляется как `NOT (любой из флагов установлен)` — сохраняется для простых потребителей Wrapper.

**Распространение по графу зависимостей** (раздел 7) действует на уровне каждого флага отдельно — производный факт наследует ровно тот флаг, из-за которого источник недостоверен. Конкретные производные факты, наследующие пониженную достоверность: CFG-рёбра, DFG-связи, alias-summary в Ring 1.

Core (Ring 0/Ring 1) только **помечает**; решение «репортить недостоверное или нет» — целиком в Wrapper.

**Статус**: `provisional`.
**Revisit Trigger**: рост доли `unknown_edge_case` относительно специфичных флагов на практике — сигнал, что классификация неполна и нужно выделять новые специфичные категории из наблюдаемых случаев.

### 8.1 Проверка целостности и логической согласованности артефакта

Разделены на два независимых механизма, решающих разные проблемы:

**A. Artifact Integrity Checksum** — обнаружение повреждения/неполной записи/битого файла. **Не может обеспечиваться Node Identity Hash'ем** (раздел 3): тот — быстрая некриптографическая функция, оптимизированная под горячий путь, не покрывает части артефакта вне AST/IR-узлов (индексы, DFG-факты, alias-summary, Requirement Set, флаги).

Отдельный, самостоятельный checksum поверх **всего** сериализованного артефакта (по сегментам — согласовано с уровневой моделью персистентности, раздел 5.1, чтобы не конфликтовать с ленивой загрузкой отдельных сегментов).

**Consolidation Candidate**: возможное слияние с Node Identity Hash через единую хэш-функцию, одновременно быструю и криптографически стойкую (кандидат — BLAKE3). Выигрыш — не нужно два прохода/два механизма. Издержка — риск, что криптостойкая функция на очень маленьких входах (отдельный AST-узел) окажется медленнее специализированной некриптографической на горячем пути инкрементального парсинга.

**Статус**: `blocked`. **Revisit Trigger**: замер throughput BLAKE3 на реалистичных размерах узлов Node Identity и сегментов артефакта, в сравнении с раздельными текущими механизмами (раздел 12). Алгоритм для отдельного (не объединённого) checksum-варианта — также `blocked`, требует замера кандидатов (BLAKE3 / xxHash3-128 / CRC32C) и оценки реального профиля риска (частота повреждений на целевой среде).

**B. Invariant Control-Sum** — обнаружение логической ошибки в коде выставления флагов (раздел 8), независимо от целостности данных.

Массив счётчиков, по одному на каждый флаг (`unsigned long long`), считается **двумя независимыми путями**:
1. **Live-накопление** — инкремент при реальном выставлении флага во время построения (побочный эффект fused-прохода, раздел 6.3)
2. **Дельта-накопление** — независимый учёт при инвалидации/пересборке узла (вычитание старых флагов, прибавление новых)

Сравнение (вычитание массивов/equality-check) — расхождение при совпадающем Node Identity root hash сигнализирует логическую ошибку именно в инкрементальной логике (не в данных).

**Параллелизм**: per-worker локальные массивы счётчиков, суммируются один раз при слиянии результатов (раздел 4.3) — нулевой contention в горячем пути.

Дешевизна операции (`+1` на u64) позволяет оставить механизм включённым в релизной сборке, не только в debug.

**Явно НЕ сливается** с Artifact Integrity Checksum (пункт A) — разная природа проверки (повреждение данных vs логическая ошибка кода); смешение ухудшило бы диагностику, сделав невозможным различение причины расхождения.

**Статус**: `provisional`.

**Открытый вопрос (сохраняется):** механизмы A и B покрывают повреждение данных и логическую ошибку счётчиков флагов индивидуально. Не покрыта отдельная задача проверки **недопустимых комбинаций** флагов на узле (например, ситуация «одновременно установлены два флага, которые архитектурно должны быть взаимоисключающими»). Нужен ли отдельный self-check pass после построения Ring 0, явно проверяющий комбинаторные инварианты — фиксируется как открытый вопрос, ни закрытый, ни отвергнутый.

## 9. Rule Compilation Pipeline

**Открытый вопрос.** JS-код правила (написанный разработчиком против некоторого API) должен быть статически превращён в Rule IR (структурный запрос + stateful bytecode). Механизм самого компилятора правил — **не спроектирован**: нужен ли встроенный JS-парсер/анализатор внутри тулчейна компиляции правил (по сути «мини-версия» части Ring 0/Ring 1, только для анализа кода самих правил)?

Этот же компилятор отвечает за построение Requirement Set (раздел 7.1) через pre-scan и обязан согласовывать intern-pool с Ring 0 (раздел 6.2).

## 10. Sub-core: Contract IR (низкий приоритет)

Отдельное, архитектурно изолированное направление — сверка API-контрактов между фронтендом и бэкендом, потенциально на разных языках.
- Не предполагает унификации AST разных языков
- Каждый язык — свой экстрактор в общий канонический Contract IR (схема эндпоинтов, типы запрос/ответ)
- Сверка идёт на уровне Contract IR↔Contract IR
- Оставлено как «база»; доработка конкретных языковых экстракторов — на усмотрение community

## 11. Ретроспективный аудит: Pure Win / Trade-off / Necessity-First

### 11.1 Pure Win (улучшение по обеим осям — скорость и память, без компромисса)

| # | Решение | Обоснование |

- Для #22: если частота точечных мелких правок окажется намного выше правок целыми поддеревьями — генерационная модель может не окупаться.
- Для #24: если преобладающий класс запросов в реальных правилах окажется точечным, а не сканирующим — выигрыш снижается, пересмотреть в свете статистики запросов.

**Статус для #26**: `blocked`, синхронизировано с решением о формате артефакта (раздел 5.1).

### 11.3 Necessity-First находки (elimination/consolidation)

**EC-1 — Context-sensitive alias analysis (раздел 6.1): предложение отложить реализацию — рассмотрено и ОТКЛОНЕНО.**

Предлагался build-order gate: строить только flow-insensitive alias facts, откладывая summary/CFL-механизм до эмпирического доказательства недостаточности грубой модели.

**Отклонено.** Обоснование: это не вопрос инфраструктурной эффективности (к которой применим принцип 0.2), а вопрос аналитической способности видеть паттерны, недоступные для плоского AST-анализа — ядро ценностного предложения всей системы (принцип 0.3). Откладывание аналитической способности запрещено правилом 0.2 в его уточнённой формулировке. Зафиксировано как явный прецедент границы применимости Necessity-First.

**EC-2 — WAL: предложение отложить как «преждевременное усложнение» — скорректировано, не отклонено.**

Вместо гейта «не строить, пока не доказана нужда» — построена изначально гибкая параметризуемая модель (раздел 5.1), где отсутствие WAL (`Direct`) — не временное упрощение, а полноправный конфигурируемый режим наравне с `Tiered`. Проблема снята архитектурно, а не отложена.

**EC-3 — Bloom filter поверх Requirement Set presence-check.** Первоначально принято как Pure Win, затем пересмотрено.

**Статус**: `blocked`. Данные: реальный размер Requirement Set при большом числе загруженных правил — определяет, оправдана ли структура сверх простого `HashSet`.

**CC-3 — Индекс «по типу узла» = сам SoA-layout, отдельная структура не строится.**

Принято, с явно задокументированным риском и митигацией — см. раздел 6.2.

**Confirmed Necessary (проверено и НЕ отменено под той же оптикой):**
- Allocation-site heap model — остаётся eager, обязательна как основа confidence-модели (раздел 2.5)
- Invariant Control-Sum и Artifact Integrity Checksum — остаются раздельными механизмами, смешение ухудшило бы диагностику (раздел 8.1)

## 14. Открытые вопросы (консолидировано)

1. **Module resolution** — разрешаем ли `import`/`require` буквально по спецификации Node.js/ESM, или закладываем расширяемость под bundler-specific resolution (webpack aliases, tsconfig `paths`, Vite)? Это ответственность Ring 0 (влияет на построение графа) или конфигурационный вход от Wrapper (уже разрешённые файл→файл рёбра)?
2. **Symbol Table / Scope Tree** — отдельная структура или набор типизированных рёбер поверх AST/IR? Как моделируются `var`-hoisting, TDZ для `let/const`, hoisting функций — через тот же механизм словаря десугаринга (2.3) или отдельно?
3. **Rule Compilation Pipeline** — механизм превращения императивного JS-кода правила в (структурный запрос + stateful bytecode); нужен ли для этого отдельный встроенный анализатор JS внутри тулчейна компиляции правил? Этот же компилятор строит Requirement Set (раздел 7.1) и согласует intern-pool с Ring 0 (раздел 6.2).
4. **Модель параллелизма для фазы построения графа (Ring 0)** — частично закрыто (раздел 4.3, независимый параллельный парсинг файлов); остаётся вопрос: параллелизм на уровне межфайловых стадий (Symbol resolution, Dependency Graph) — по файлам или только на уровне отдельных queries внутри Salsa-графа?
5. **Классификация query** (streamable / non-local / fixpoint, включая alias-queries) — статически при компиляции правила, или динамически в рантайме query engine?
6. **Синтаксис Structural Query Language** для join-слоя между графами — не определён.
7. **Типы индексов по умолчанию** — «по типу узла» закрыто через SoA-layout (раздел 6.2); «по имени идентификатора» — предполагается обязательным; «оператор, литерал, глубина AST, CFG-reachability» — под вопросом. Полный список сверх этого и возможность кастомных индексов по запросу правила — не определены.
8. **Orchestration stateful-фазы** — Sequential vs Independent обработка кандидатов внутри одного правила: декларируется правилом явно в Rule IR, или query engine выводит автоматически из анализа bytecode на предмет разделяемого состояния.
9. **Type Layer — механизм** (раздел 2.10) — раз периметр включает TS, слой типов признан релевантным (см. журнал решений #1), но конкретный механизм (интеграция с TS type checker для типизированных файлов, поведение для чистого JS — best-effort inference или явный отказ) не проработан.
10. **Contract IR (sub-core)** — не проработан, сознательно отложен, низкий приоритет (раздел 10).
11. **Формат артефакта на диске** (раздел 5.1) — заблокирован до расчёта веса.
12. **Порог `context_saturated`** (раздел 6.1) — заблокирован до сбора данных по Roadmap.
13. **Разрешение конфликта между heap-моделями** (раздел 2.5) — если правило запрашивает name-based факты и они расходятся с allocation-site предсказаниями, механизм разрешения не сформулирован (в предыдущей симметричной модели была кросс-валидация и уточнение точности при конфликте — в асимметричной модели утрачено, замена не спроектирована).
14. **Self-check pass на недопустимые комбинации флагов** (раздел 8.1) — механизмы A/B покрывают повреждение данных и логическую ошибку счётчиков индивидуально, но проверка комбинаторных инвариантов (одновременная установка архитектурно взаимоисключающих флагов) не покрыта; нужен ли отдельный self-check pass — открыт.
